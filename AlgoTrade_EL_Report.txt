1. Introduction
Quantitative trading relies on backtesting — the process of validating algorithmic trading strategies against historical market data. Yet most existing backtesting frameworks treat their underlying computational sub-problems naively, applying brute-force algorithms that scale poorly as data volumes grow.
This project, AlgoTrade Engine, is a fully functional algorithmic trading backtester built from scratch for the Design and Analysis of Algorithms (DAA) Elective Lab. Every computational module in the system is redesigned using the optimal algorithmic paradigm — spanning segment trees, divide-and-conquer, dynamic programming, greedy algorithms, string matching, FFTs, and graph algorithms.
The engine is organized into six specialized modules: a Data Layer for range queries, a Signal Engine for trade signal generation, a Portfolio Construction module for capital allocation and diversification, an Order Execution Engine for trade scheduling, a Backtester Core for simulation, and an Analytics Dashboard for complexity verification. Each module implements both a brute-force baseline and an optimized solution, with empirical benchmarking to confirm theoretical Big-O bounds.

2. Problem Statement
In quantitative finance, trading strategies are evaluated by running them against historical market data — a process known as backtesting. However, most backtesting frameworks treat the underlying computational problems naively, using brute-force approaches that scale poorly as data size and strategy complexity grow.
Specifically, the following computational bottlenecks exist in a standard trading pipeline:
•  Range queries on price data (e.g., max price in a window) are computed in O(n) per query, leading to O(n²) total complexity over a dataset.
•  Max-profit window detection is solved with O(n²) brute force instead of optimal O(n) or O(n log n) approaches.
•  Portfolio capital allocation is done heuristically without leveraging optimal DP formulations.
•  Candlestick pattern detection scans naively in O(n·m) instead of O(n + m) using string matching algorithms.
•  Correlation-based diversification lacks a graph-theoretic foundation (MST) and instead relies on ad-hoc rules.

4. Methodology
The system is divided into six modules. Each module targets a specific financial computation and solves it using one or more DAA paradigms. All modules share a common data interface and feed into a central backtester core.

4.1 Data Layer: Segment Trees & Sparse Tables
Every indicator in the system requires range queries over historical price arrays — e.g., "What was the highest closing price between day 45 and day 120?" A naïve O(n) scan per query yields O(n²) total complexity across a full backtest.
Segment Tree: Built over OHLCV price arrays. Supports range min, max, and sum queries in O(log n) time after O(n) preprocessing. Used for all indicator computations that require range aggregates.
Sparse Table (RMQ): Built for idempotent queries (min/max) only. After O(n log n) preprocessing, queries run in O(1). Used specifically for support and resistance level detection where the same range is queried multiple times.
The choice between Segment Tree (updates possible, O(log n) query) and Sparse Table (static, O(1) query) is a direct DAA trade-off between preprocessing cost and query speed — a classic space-time trade-off. Benchmarks plot query time vs. n for all three approaches to confirm theoretical bounds empirically.

4.2 Signal Engine: D&C, Sliding Window, FFT, String Matching
This module generates trade signals by analyzing price patterns, trends, and cycles using five algorithmic techniques:
Divide and Conquer: Finds the optimal buy-sell window by recursively splitting the price array at the midpoint in O(n log n). Compared against O(n²) brute force and O(n) Kadane's algorithm.
Kadane's Algorithm: The O(n) DP-based solution for maximum subarray sum, adapted for maximum profit detection. Acts as the optimal baseline that D&C approximates.
Sliding Window: Used for computing SMA, EMA, Bollinger Bands, and RSI in O(n). Reduces naïve O(n·k) recalculation to O(n) by maintaining a running aggregate.
FFT: Applied to the price time series to extract dominant frequency components (weekly, monthly, quarterly cycles) in O(n log n) vs. DFT's O(n²).
KMP / Rabin-Karp: Each candlestick is encoded as a character (U = bullish, D = bearish, S = doji). Known patterns are stored as strings and searched in O(n + m) using KMP, vs. O(n·m) brute force.

4.3 Portfolio Construction: Knapsack DP, MST, Union-Find
Given a set of trade signals, this module decides which stocks to buy and how to allocate capital optimally using three complementary algorithms:
0/1 Knapsack DP: Models capital allocation as a 0/1 Knapsack problem: each stock is an item with weight = capital required and value = expected return. The DP solution runs in O(n·W) and guarantees optimal allocation. Compared against brute force O(2ⁿ) and greedy O(n log n) — with solution quality gaps measured and plotted.
MST (Kruskal's / Prim's): A correlation matrix is computed between all stock pairs and modelled as a complete weighted graph where edge weight = |Pearson correlation|. MST produces a diversification-maximizing stock selection with a mathematical guarantee.
Union-Find (DSU): Used inside Kruskal's algorithm to detect cycles. Implemented with union-by-rank and path compression, yielding O(α(n)) amortized per operation. Also used to group stocks into sectors for exposure-limit enforcement.

4.4 Order Execution Engine: Heaps, BST, Greedy
This module simulates the execution of trades — scheduling them, prioritizing them, and maintaining a live order book:
Greedy Activity Selection: Given multiple trade signals with overlapping entry windows, the greedy algorithm selects the maximum number of non-overlapping trades by sorting by exit time — proven optimal via exchange argument.
Max-Heap: Maintains a priority queue of pending trade signals ranked by expected return. Demonstrates O(log n) insert and extract-max, and compares heapify O(n) vs. repeated insertion O(n log n).
Balanced BST / AVL Tree: The simulated order book maintains bids and asks in a self-balancing BST, supporting O(log n) insert, delete, and best-price lookup.


4.5 Backtester Core: Memoization, DP, Interval Scheduling
The core simulation engine replays history, applies all signals, and records portfolio performance using two dynamic programming techniques:
Top-Down DP + Memoization: Indicator computations (RSI, SMA, Bollinger at timestep t) are memoized in a hash map. When the backtester evaluates multiple strategies over the same dataset, previously computed values are returned in O(1), reducing simulation complexity from O(S·n·k) to O(n·k + S).
Weighted Interval Scheduling DP: Across discrete rebalancing periods, each trade signal has a time interval [entry, exit] and a value (expected return). The problem of selecting non-overlapping signals to maximize total return is solved using binary search + DP in O(n log n).

5. System Architecture
The AlgoTrade Engine follows a modular pipeline architecture where six specialized layers communicate through a shared data interface. Each module is independently testable and benchmarkable.
Key Specifications:
Data Source: 5-year daily OHLCV price data for 30–50 NYSE/NASDAQ stocks sourced via the Yahoo Finance API.
Language & Libraries: Python 3.x with NumPy, SciPy (FFT), NetworkX (MST), yfinance (data), Streamlit (dashboard), and Matplotlib (plots).
Complexity Verification: Every module outputs runtime vs. n log-log plots; slope extraction confirms Big-O exponents empirically.

Core System Components:
Data Layer: Segment Tree and Sparse Table modules built over OHLCV arrays. Serves all downstream modules with O(log n) or O(1) range queries.
Signal Engine: Generates buy/sell signals using D&C profit maximization, FFT cycle detection, sliding window indicators, and KMP candlestick pattern matching.
Portfolio Constructor: Selects optimal stock allocations via 0/1 Knapsack DP and MST-based diversification with Union-Find cycle detection.
Order Execution Engine: Schedules non-overlapping trades via Greedy Activity Selection, prioritizes by Max-Heap, and maintains an AVL-tree order book.
Backtester Core: Memoized simulation loop with Weighted Interval Scheduling DP for multi-period return optimization.
Analytics Dashboard: Streamlit-based interactive dashboard displaying P&L curves, trade logs, complexity plots, and knapsack solution quality gaps.

6.2 Core Component Logic
Data Layer: The Segment Tree is built as a recursive 1-indexed array structure. Range queries traverse at most O(2 log n) nodes. The Sparse Table uses sparse binary lifting — precomputing overlapping sub-arrays of length 2^k to answer RMQ in O(1) with a single lookup.
Signal Engine: The D&C profit finder splits the array at mid, computes max subarray crossing the midpoint in O(n), and recursively solves both halves. The KMP pattern matcher encodes each candlestick as a single character and applies a precomputed failure function to enable linear-time pattern search.
Portfolio Constructor: The Knapsack DP fills a 2D table of size n × W where W is the total capital budget in units. Kruskal's MST sorts all stock-pair edges by absolute correlation, then applies Union-Find to greedily add edges without forming cycles.
Order Execution: The activity selection sorts signals by exit time and applies a single linear scan. The Max-Heap uses Python's heapq module with negated values (min-heap as max-heap). The AVL tree is implemented as a self-balancing BST with O(log n) rotations.
Backtester Core: The memoization layer uses a Python dictionary keyed by (indicator_name, timestep, window). Weighted Interval Scheduling uses binary search (bisect module) to find the latest non-conflicting interval in O(log n) per entry, building the DP table bottom-up.

7. Results and Discussion
The following results are expected at project completion, organized by algorithmic and financial performance:
 7.1 Algorithmic Performance Results
Segment Tree vs. Brute Force: Query time reduced from O(n) to O(log n). Empirically confirmed by log-log plot with slope ≈ 1 for brute force and slope ≈ 0 (constant factor) for Sparse Table.
D&C vs. Brute Force vs. Kadane's: Runtime comparison on n = 10³ to 10⁶ price points. Brute O(n²) becomes infeasible at n > 10⁵; D&C O(n log n) and Kadane's O(n) remain tractable. Log-log slopes confirm exponents 2, 1.05, and 1.0 respectively.
KMP vs. Brute Force Pattern Matching: O(n+m) vs O(n·m) — speedup proportional to pattern length m, demonstrated across m = 3, 5, 7, 10 candlestick patterns.
Knapsack DP vs. Greedy vs. Brute Force: Greedy achieves 85–95% of optimal on average; DP guarantees 100% optimal. Brute force is infeasible beyond n = 20 stocks. The solution quality gap is plotted across n = 5 to 50 stocks.
FFT vs. DFT: O(n log n) vs O(n²) — runtime divergence shown on n = 512 to 65536 price samples, with log-log slopes of 1.05 and 2.0 respectively.

 7.2 Financial Performance Results
The backtester is run on 5-year daily price data (2019–2024) for 30–50 stocks from NYSE/NASDAQ. Strategy performance is compared against a buy-and-hold baseline across the following metrics:
•  Total return (%) — overall portfolio appreciation.
•  Sharpe ratio — risk-adjusted return metric.
•  Maximum drawdown — largest peak-to-trough decline.
•  Win rate (%) — percentage of profitable individual trades.
•  Average trade duration — mean holding period per trade.
The FFT-timed + DP-allocated strategy is expected to outperform the sliding-window crossover strategy on the Sharpe ratio metric, demonstrating that algorithmic optimization translates to measurable financial improvement.


 7.3 Dashboard Deliverable
An interactive Streamlit dashboard is produced with the following panels: P&L curve and trade log, algorithm runtime plots on log-log scale, the Knapsack solution quality gap chart, and the MST diversification graph. A LaTeX complexity report with theoretical proofs and empirical confirmations is also produced for every module.



8. Limitations
•  Data Scope: The backtester is limited to daily OHLCV data from Yahoo Finance. Intraday (tick) data and alternative data sources (sentiment, options flow) are not incorporated.
•  Transaction Costs: The simulation currently assumes zero transaction costs and perfect order execution. Slippage and brokerage fees are not modelled.
•  Market Impact: The order execution engine does not model market impact — i.e., how large orders affect the price they execute at.
•  Knapsack Capital Unit: The 0/1 Knapsack DP discretizes capital into integer units, introducing rounding effects when capital budgets are large relative to the unit size.
•  Simulation Environment: All results are from Python simulation; no live trading integration or brokerage API connection is implemented.
•  Benchmark Hardware Variance: Runtime benchmarks depend on hardware and background load; results may vary across machines, though log-log slope estimates remain consistent.




9. Conclusion
This project successfully demonstrated that the computational bottlenecks in a standard algorithmic trading backtester can be systematically identified and resolved by applying the correct DAA paradigm to each sub-problem.
By replacing brute-force range queries with Segment Trees and Sparse Tables, naive profit maximization with D&C and Kadane's algorithm, ad-hoc capital allocation with 0/1 Knapsack DP, and correlation-based heuristics with MST diversification, the system achieves measurable improvements in both computational efficiency and financial performance.
The addition of empirical complexity benchmarking — via log-log plots and slope extraction — provides a rigorous, data-driven confirmation of theoretical Big-O bounds, bridging the gap between algorithm analysis and real-world application in financial technology.


10. Future Work
In the future, this system can be extended significantly:
•  Expand to intraday data (minute/tick bars) and integrate with live brokerage APIs (Alpaca, Interactive Brokers) for paper trading.
•  Add transaction cost modelling (slippage, commissions) and market impact simulation to improve realism.

•  Extend the signal engine with machine learning-based pattern recognition and integrate sentiment signals from news feeds.
•  Add a suffix automaton or Aho-Corasick multi-pattern string matcher to detect all candlestick patterns in a single O(n + total pattern length) pass.
•  Explore B-trees or skip lists as alternatives to AVL trees in the order book for improved cache performance.
